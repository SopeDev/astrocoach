# Project Decisions

Last updated: 2026-09-04

## Product scope

- The product direction is governed by `astrocoach_mvp_product_guide_v0.1.md`, `astrocoach_prompt_architecture_v0.2.md`, and the initial implementation brief.
- EXPLORE and RECOGNIZE are implemented in the current product loop. DEEP_EXPLORE and INTEGRATE remain future product direction.
- Begin EXPLORE with a fresh “What’s going on?” message while completed onboarding remains private background context rather than appearing as chat history. Persist each user message before generation, store the visible reply separately from structured internal signals, and show an explicit retry state instead of substituting a generic fallback response when chat generation fails.
- Evolutionary and Kabbalistic astrology is AstroCoach's primary symbolic and developmental framework. It should produce confident, holistic interpretations when relevant, while lived experience remains authoritative about how symbolism manifests and must be allowed to revise or reject a reading.
- Express that philosophy through product behavior rather than repeated user-facing disclaimers. Interface copy should use a warm, plain reflective-partner voice and lead with why each step matters personally; expose technical calculation details only when they are needed for an informed choice or error recovery.
- Keep the technical natal-chart review route hidden from the normal onboarding flow. After initial intent, combine the chart, selected life areas, and optional current context to generate provisional discovery questions that test relevance against lived experience.
- Use two-stage initial discovery: generate exactly three opening questions from chart and intent context, then exactly two finalizing questions from that context plus the first three answers. Users may revise within each stage, but generating question four closes the opening stage so adaptive follow-ups retain a stable source context.
- Treat cognitive-mode changes as application-owned and user-controlled. EXPLORE readiness must be supported by multiple recent structured signals; the interface offers a plain-language choice rather than changing modes automatically. Declining an invitation requires new lived evidence before it can be offered again.
- Keep cognitive mode names internal. The chat header remains “AstroCoach” and may use plain contextual subtitles, while a pending mode-transition invitation temporarily replaces the regular composer with an explicit user choice.
- In RECOGNIZE, present one small recurring relationship naturally without asking for confirmation in conversational prose. Application-owned controls collect `YES_EXACTLY`, `PARTLY`, `NO`, or `LET_ME_EXPLAIN`; only `YES_EXACTLY` validates the candidate, while saving to My Map remains a separate application-owned choice.
- Persist candidate evaluation on the source assistant message's structured internal state. `PARTLY` records partial recognition, `LET_ME_EXPLAIN` records no evaluation, and either is passed explicitly with the pending candidate and supporting evidence into the next RECOGNIZE generation.
- EXPLORE must vary its conversational move and ask a question only when the answer would materially improve understanding; serial question and multiple-choice cadence is explicitly discouraged.
- RECOGNIZE may begin with a focused hypothesis-testing stage when competing explanations remain material. A Candidate Pattern is presented only after lived evidence supports the smallest defensible relationship, and broadened scope requires an independent example or cross-context contrast.
- Natal context is supplied to discovery, EXPLORE, and RECOGNIZE at every astrology communication setting. A global `astrologyStyle` preference controls only how explicitly relevant holistic reasoning appears, while a separate `astrologyFamiliarity` preference controls vocabulary and explanation depth; neither changes whether the evolutionary/Kabbalistic framework is used or the rule that astrology alone cannot establish lived facts, recurrence, event causation, or consequential advice.
- Keep authored astrological references versioned and separate from chart facts and visible messages. Preserve the original source alongside a concise product-language adaptation, retrieve only the exact material supported by the calculated chart, and supply it as private interpretive context. Reference entries offer possible expressions and developmental directions rather than established biography or destiny.
- Keep one canonical English authored-interpretation catalog per category under `src/data/astrology`, with stable entry identifiers and a shared project loader. Models translate retrieved interpretations as part of their normal localized response; do not maintain duplicate localized authored catalogs. For the generated Chart-at-a-glance browsing surface, store a faithful Spanish display presentation alongside the canonical English synthesis so reopening the page does not require another model call. Keep source provenance at the catalog and model-context envelope boundaries rather than repeating it on every interpretation entry.
- Keep karmic Moon and Saturn interpretations as a structurally labeled secondary lens on the same natal placements, not as additional chart factors or independent lived evidence. Matching both the general and karmic entries must not increase a placement's significance score merely because it has two authored sources. Midheaven-by-sign interpretations require a known birth time and describe possible forms of vocation and public contribution rather than promised careers or outcomes.
- Persist each user's synthesized natal interpretation separately from deterministic chart data. Key it to the chart input hash, interpretation schema version, and catalog versions so unchanged charts reuse one synthesis while chart or library changes invalidate it. Store exactly five English themes with stable semantic slots: identity (Sun plus Ascendant, or Moon when birth time is unknown), karmic (nodal familiar-pattern axis plus Saturn and Moon), mission (nodal developmental axis plus Midheaven and Sun, omitting Midheaven when birth time is unknown), and two chart-specific emergent themes. Each theme retains supporting factor IDs and explicit birth-time uncertainty; a deterministic synthesis is the fallback when model generation is unavailable.
- Rank composite chart factors deterministically from factor class, chart rulership, angular placement, and aspect strength. Aspects may affect prominence but receive no authored meaning while aspect interpretations remain deferred. Initial Discovery, EXPLORE, and RECOGNIZE receive only a topic-relevant bounded subset of themes and matched authored material, never the full raw chart dump. Every stored and retrieved envelope must carry `source: "natal_interpretation"` and `evidenceStatus: "symbolic_hypothesis_not_user_evidence"` so symbolic material cannot count as lived observations or satisfy recognition thresholds.
- AstroCoach's baseline voice is a perceptive trusted friend who is highly fluent in astrology: conversational, intimate without presumption, simple in language, and capable of natural correction. It begins with the interpretive substance, uses direct language and concrete contrasts, and embodies its epistemic standards without narrating them unless the user asks about its method or limits. This product voice remains separate from the user's communication preferences and avoids generic therapy-speak, report-style enumeration, stacked hedging, and compulsory follow-up questions.
- AstroCoach validates lived and emotional reality without automatically validating the user's explanation. It may discuss an absent person's explicit communication and observable behavior, but keeps unobservable motives and psychology tentative; challenge should move gradually from attunement to precision without becoming either sycophantic or prosecutorial.
- Visible astrology must make a new contribution to the current turn. Do not repeatedly reuse a placement as rhetorical support, give symbolic possibilities the certainty of biography, or use a partial chart to claim access to an absent person's inner life.
- Birth time is optional. Houses and angles must not be calculated or presented when it is unavailable.
- Store birth dates as calendar dates and known birth times as minutes after midnight. A null birth time explicitly means unknown and must remain distinct from midnight.
- Use the MIT-licensed Celestine engine, pinned to an exact version behind a project-owned adapter, for local natal calculations without an external API. Include Chiron, and use Placidus houses and Mean Lunar Nodes for exact-time charts. For unknown-time charts, calculate planets, Chiron, and Mean Lunar Nodes at local noon as an explicitly uncertain reference; retain node signs but omit node houses, all other houses, angles, and aspects.
- Retain Celestine for the prototype despite a verified Pluto longitude discrepancy of about 13 arcminutes against Kepler 7.0 and NASA/JPL Horizons for a November 2015 reference chart. Reassess the planetary ephemeris before interpretation becomes sensitive to sign boundaries, house cusps, or tight aspect orbs.
- Use Auth.js with database-backed sessions and Google OAuth as the first authentication method. Email/password authentication remains a separate future slice so registration, verification, recovery, rate limiting, and account linking can be designed together.
- Detailed high-stakes safety architecture remains deferred for the prototype.

## Application architecture

- Use the Next.js App Router with TypeScript and React Server Components by default.
- Use Tailwind CSS for styling and add shadcn/ui components selectively rather than adopting a broad component layer upfront.
- Support English and Spanish from the first onboarding flow. Locale values use stable `en` and `es` identifiers so additional languages can be added later.
- Localized product routes begin with `/{locale}`. The selected locale is stored on the user and in an HTTP-only `astrocoach-locale` cookie so server-rendered document language and navigation remain consistent before full authentication exists.
- The root language-selection route checks the server-side session before rendering. Authenticated users bypass language and sign-in screens and resume through the existing stage-aware landing resolver using their saved locale.
- After onboarding has started, changing the account locale requires an explicit language selection. Cookie-to-account synchronization is limited to the first authenticated handoff, preventing a stale URL or cookie from silently changing an established preference.
- Support system, light, and dark color themes with `next-themes`.
- Store astrology familiarity and communication style on the user profile with defaults of `basic` and `balanced`. Collect them alongside initial intent after birth information and expose the same choices in Account so changes affect future generations without rerunning onboarding.
- Keep the theme control directly available during onboarding, and persist authenticated changes to the user profile. After onboarding, appearance is an Account setting and the shell header uses that space for the user avatar.
- AstroCoach is a mobile-first progressive web application. Every interface starts with phone ergonomics, touch targets, safe-area behavior, and standalone display constraints before adding tablet or desktop enhancements.
- Completed discovery leads through a one-time Chart-at-a-glance reveal and concise product orientation, then into a Home-first application shell rather than directly into chat. The primary mobile navigation remains Home, Conversations, and My Map, with Account available from the header avatar.
- Home is the starting point for a new EXPLORE conversation; Conversations reopens saved threads. My Map is the eventual parent hub for the natal chart and the user-owned Map items that revolve around it. Patterns, Insights, and Practices are the defined Map-item categories; only Patterns are currently implemented. The chart lives at `/{locale}/chart` for now and will be linked from the future Map hub rather than receiving a separate primary-navigation item.
- Chart-at-a-glance theme cards may start EXPLORE conversations from an editable user-authored prompt. Persist the stable selected theme ID separately as provenance-safe message metadata, pin that theme in first-turn retrieval, and never copy its synthesis into the conversation as if it were user testimony.
- Conversation archiving is recoverable and separate from its EXPLORE/RECOGNIZE lifecycle status. Archived conversations are read-only, excluded from recent-conversation selection and generation actions, and remain reviewable until restored or permanently deleted. Permanent deletion is available only after archiving and atomically removes the conversation, its messages, and Patterns saved from it. Conversation-level actions are grouped in an expandable three-dot row menu so additional actions can be added without crowding the list.
- Export conversations as a versioned JSON document from the conversation row menu, including persisted conversation lifecycle data and complete message content and metadata. Do not attach current astrology familiarity or communication-style preferences to historical messages; include those settings only after immutable per-message snapshots exist.
- Saved Pattern wording is user-owned and may be edited directly without another model call or revalidation. Removing a Pattern from the active Map archives it recoverably rather than deleting its statement or conversation provenance; archived Patterns can be restored.
- Maintain an installable web app manifest and platform app icons. Add offline caching or push behavior only through deliberate, separately verified slices so stale application code or private user data is not cached accidentally.
- Use Prisma 7 as the ORM and migration system for PostgreSQL. During solo early development, local, preview, and production environments share the Prisma Postgres database connected through the Vercel Marketplace; split environments before broader testing or routine schema-changing previews.
- Use Prisma's PostgreSQL driver adapter. Prefer standard `DATABASE_URL` and `DIRECT_URL` names; accept the Vercel integration's generated `POSTGRES_URL` and resource-prefixed `astro_*` aliases so deployment is not coupled to manually copied secrets.
- Resolve all personal data through the authenticated Auth.js user. The seeded development identity remains fixture data only and must not be used as a runtime identity.

## External services

- Keep all external-service credentials server-only. Never expose them through `NEXT_PUBLIC_*` variables.
- Use a server-mediated external geocoder for prototype birthplace search. Preserve coordinates and an IANA timezone identifier, then resolve the historically applicable offset for the birth date and time.
- Use GeoNames for prototype populated-place search and timezone lookup. Treat its place ID as the submitted selection, re-fetch authoritative coordinates server-side, and derive the historical UTC instant locally from the returned IANA timezone.
- Use the OpenAI Responses API when conversational AI is implemented and request application-facing metadata through Structured Outputs.
- Keep the initial chat implementation stateless with respect to OpenAI: AstroCoach owns conversation history in PostgreSQL, sends the relevant recent thread on each request, and disables OpenAI response storage. Add token streaming only as a separately verified UX improvement.
- Voice input is transcript-first: authenticated users may record up to two minutes, the temporary audio is sent directly for server-side transcription, and only the resulting editable text enters the existing message flow. Do not persist recordings or send a transcript automatically without user review.
- Use the same voice-recording and transcription behavior in the Home new-conversation composer and existing conversation composer so starting context has input parity.
- The OpenAI model is configured with `OPENAI_MODEL`. The development default is `gpt-5.6-luna`, selected as the current cost-sensitive model; it can be changed without code changes.
- Audio transcription uses the same server-only OpenAI credential and a separately configurable `OPENAI_TRANSCRIBE_MODEL`, defaulting to `gpt-transcribe`.

## Delivery

- The application is designed for Vercel deployment and uses environment-based configuration.
- Development uses npm and commits the generated lockfile.
- The user exclusively handles Git staging, commits, and pushes. The coding agent may inspect Git state but must not mutate it.
- Production builds currently use Next.js's webpack builder and the TypeScript compiler API because the development execution environment blocks Turbopack's internal localhost binding and detached TypeScript CLI process.
- Each implementation slice must leave linting, type checking, and the production build passing.
