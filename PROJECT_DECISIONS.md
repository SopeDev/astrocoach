# Project Decisions

Last updated: 2026-09-07

## Product scope

- The product direction is governed by `astrocoach_mvp_product_guide_v0.1.md`, `astrocoach_prompt_architecture_v0.2.md`, and the initial implementation brief.
- EXPLORE, RECOGNIZE, DEEP_EXPLORE, and the first deliberately small INTEGRATE loop are implemented. These are independent cognitive modes rather than sequential levels, and DEEP_EXPLORE is not a prerequisite for recognizing or persisting Insights.
- Begin EXPLORE with a fresh “What’s going on?” message while completed onboarding remains private background context rather than appearing as chat history. Persist each user message before generation, store the visible reply separately from structured internal signals, and show an explicit retry state instead of substituting a generic fallback response when chat generation fails.
- Evolutionary and Kabbalistic astrology is AstroCoach's primary symbolic and developmental framework. It should produce confident, holistic interpretations when relevant, while lived experience remains authoritative about how symbolism manifests and must be allowed to revise or reject a reading.
- Express that philosophy through product behavior rather than repeated user-facing disclaimers. Interface copy should use a warm, plain reflective-partner voice and lead with why each step matters personally; expose technical calculation details only when they are needed for an informed choice or error recovery.
- Keep the technical natal-chart review route hidden from the normal onboarding flow. After initial intent, combine the chart, selected life areas, and optional current context to generate provisional discovery questions that test relevance against lived experience.
- Use two-stage initial discovery: generate exactly three opening questions from chart and intent context, then exactly two finalizing questions from that context plus the first three answers. Users may revise within each stage, but generating question four closes the opening stage so adaptive follow-ups retain a stable source context.
- Treat cognitive-mode changes as application-owned and user-controlled. The first qualifying EXPLORE readiness signal immediately offers a plain-language choice rather than changing modes automatically, because RECOGNIZE is itself the user-controlled hypothesis-evaluation stage. After a declined invitation, require corroborated qualifying signals from subsequent turns before offering it again.
- Keep cognitive mode names internal. The chat header remains “AstroCoach” and may use plain contextual subtitles, while a pending mode-transition invitation temporarily replaces the regular composer with an explicit user choice.
- RECOGNIZE means recognizing something worth keeping. The system classifies the candidate as a Pattern when it describes recurrence supported by distinct lived observations, or as an Insight when it is a meaningful evidence-grounded understanding that does not claim recurrence; the user is not asked to choose the type. Application-owned controls collect `YES_EXACTLY`, `PARTLY`, `NO`, or `LET_ME_EXPLAIN`; only `YES_EXACTLY` validates the candidate, while saving to My Map remains a separate application-owned choice.
- Accuracy alone does not make a reflection an Insight. A Map candidate must add consequential understanding beyond compressing the user's facts, labeling a temporary external situation, repeating a causal link the user already supplied, or polishing their wording. Apply a counterfactual test to every proposed Insight: if the immediate circumstances disappeared, the understanding must still say something useful about the person. Non-recurring Insights remain valid, but if their value disappears with the producing situation they are conversational understanding rather than Map items; RECOGNIZE returns to EXPLORE or pauses.
- Persist candidate evaluation on the source assistant message's structured internal state. `PARTLY` records partial recognition, `LET_ME_EXPLAIN` records no evaluation, and either is passed explicitly with the pending candidate and supporting evidence into the next RECOGNIZE generation.
- EXPLORE must vary its conversational move and ask a question only when the answer would materially improve understanding; serial question and multiple-choice cadence is explicitly discouraged.
- RECOGNIZE may begin with focused hypothesis testing when competing explanations remain material. A Candidate Map item is presented only after lived evidence supports the smallest defensible understanding. Pattern claims require supported recurrence and broadened Pattern scope requires an independent example or cross-context contrast; Insights do not acquire an artificial recurrence requirement.
- DEEP_EXPLORE begins only from a user-selected, recognized Map item and pursues greater accuracy or meaning one dimension at a time rather than re-proving the item or prescribing change. Any understanding worth keeping returns through RECOGNIZE with an explicit distinction between a separate new Map item and a revision to the focal item; rejecting the candidate returns the conversation to DEEP_EXPLORE.
- INTEGRATE exists to make a recognized understanding available in lived experience so awareness and meaningful choice become possible; it is not primarily a Practice generator or behavior-change mode. Its first loop is intentionally small: user intention → exactly one bounded Practice → life → a small observation → new evidence. Practices combine one supported purpose and primitive with model-personalized wording and cues, remain experiments rather than rules, and must never be prescribed by astrology.
- Natal context is supplied to discovery, EXPLORE, RECOGNIZE, and DEEP_EXPLORE at every astrology communication setting. A global `astrologyStyle` preference controls how explicitly relevant holistic reasoning appears in conversations, while a separate `astrologyFamiliarity` preference controls vocabulary and explanation depth there; neither changes whether the evolutionary/Kabbalistic framework is used or the rule that astrology alone cannot establish lived facts, recurrence, origins, event causation, Map connections, or consequential advice. Initial Discovery is a deliberate exception in presentation: astrology and both preferences guide the depth of its private hypotheses, but every visible onboarding question remains technical-free lived-experience language.
- Keep authored astrological references versioned and separate from chart facts and visible messages. Preserve the original source alongside a concise product-language adaptation, retrieve only the exact material supported by the calculated chart, and supply it as private interpretive context. Reference entries offer possible expressions and developmental directions rather than established biography or destiny.
- Keep one canonical English authored-interpretation catalog per category under `src/data/astrology`, with stable entry identifiers and a shared project loader. Models translate retrieved interpretations as part of their normal localized response; do not maintain duplicate localized authored catalogs. For the generated Chart-at-a-glance browsing surface, store a faithful Spanish display presentation alongside the canonical English synthesis so reopening the page does not require another model call. Keep source provenance at the catalog and model-context envelope boundaries rather than repeating it on every interpretation entry.
- Keep karmic Moon and Saturn interpretations as a structurally labeled secondary lens on the same natal placements, not as additional chart factors or independent lived evidence. Matching both the general and karmic entries must not increase a placement's significance score merely because it has two authored sources. Midheaven-by-sign interpretations require a known birth time and describe possible forms of vocation and public contribution rather than promised careers or outcomes.
- Persist each user's synthesized natal interpretation separately from deterministic chart data. Key it to the chart input hash, interpretation schema version, and catalog versions so unchanged charts reuse one synthesis while chart or library changes invalidate it. Store exactly five English themes with stable semantic slots: identity (Sun plus Ascendant, or Moon when birth time is unknown), karmic (nodal familiar-pattern axis plus Saturn and Moon), mission (nodal developmental axis plus Midheaven and Sun, omitting Midheaven when birth time is unknown), and two chart-specific emergent themes. Each theme retains supporting factor IDs and explicit birth-time uncertainty; a deterministic synthesis is the fallback when model generation is unavailable.
- Include the natal-chart schema version in the chart input hash so calculation-policy changes invalidate dependent interpretations even when the user's birth inputs have not changed.
- Rank placements deterministically from factor class, chart rulership, and angular placement. Represent each eligible major aspect as its own ranked, provenance-bearing factor using exact body, type, orb, strength, applying, and out-of-sign metadata plus a versioned authored aspect interpretation; do not also boost its planets' scores, because that would double-count the same relationship. Supply all exact-time aspects and only unknown-time aspects stable across the sampled local day to Chart-at-a-glance generation. EXPLORE, RECOGNIZE, and DEEP_EXPLORE may use bounded relevance retrieval after the conversation begins. Initial Discovery instead receives one complete frozen astrology snapshot containing the canonical natal chart, all five generated themes, current planetary positions, every active major transit-to-natal contact, and deterministic links from those contacts to activated natal aspects. All natal and transit interpretation material remains `symbolic_hypothesis_not_user_evidence` and cannot count as lived observations or satisfy recognition thresholds.
- Maintain one application-wide, house-free current-transit position snapshot calculated locally with the pinned Celestine engine and lazily refreshed after 12 hours when onboarding questions or a new conversation needs it; no scheduled job or external astrology request is required. Use an optimistic singleton-row update so concurrent refreshes converge on one stored snapshot. Explicitly configure the Sun through Pluto, Moon, Chiron, and Mean North Node as transiting bodies and conjunction, sextile, square, trine, and opposition as transit aspects. Derive each person's transit-to-natal aspects deterministically on the server from that shared snapshot, then freeze the positions and personal aspects into Initial Discovery and each new conversation's immutable context. Transit positions never contain houses; natal houses and angles remain available only for known birth times. Current transits may identify what is especially active now but cannot establish or cause lived events, and all noon-reference natal contacts remain time-uncertain.
- AstroCoach's baseline voice is a perceptive trusted friend who is highly fluent in astrology: conversational, intimate without presumption, simple in language, and capable of natural correction. It begins with the interpretive substance, uses direct language and concrete contrasts, and embodies its epistemic standards without narrating them unless the user asks about its method or limits. This product voice remains separate from the user's communication preferences and avoids generic therapy-speak, report-style enumeration, stacked hedging, and compulsory follow-up questions.
- Apply the same core voice to every user-visible model generation, including persistent Chart-at-a-glance content. In Initial Discovery, opening questions may lead with a confident but correctable human observation selected from chart symbolism; final questions must visibly reuse concrete words from two different user answers. In Chart at a glance, titles, syntheses, and possible expressions must use only ordinary lived-experience language, while an expandable supporting-factors section may show the exact technical astrology as provenance for users who want it. Both generation paths reject technical astrology in the primary prose fields and make one corrective retry before using their human-language fallbacks.
- AstroCoach validates lived and emotional reality without automatically validating the user's explanation. It may discuss an absent person's explicit communication and observable behavior, but keeps unobservable motives and psychology tentative; challenge should move gradually from attunement to precision without becoming either sycophantic or prosecutorial.
- Visible astrology must make a new contribution to the current turn. Do not repeatedly reuse a placement as rhetorical support, give symbolic possibilities the certainty of biography, or use a partial chart to claim access to an absent person's inner life.
- Birth time is optional. Houses and angles must not be calculated or presented when it is unavailable.
- Store birth dates as calendar dates and known birth times as minutes after midnight. A null birth time explicitly means unknown and must remain distinct from midnight.
- Use the MIT-licensed Celestine engine, pinned to an exact version behind a project-owned adapter, for local natal calculations without an external API. Include Chiron, and use Placidus houses and Mean Lunar Nodes for exact-time charts. For unknown-time charts, calculate planets, Chiron, and Mean Lunar Nodes at local noon as an explicitly uncertain reference; retain node signs but omit node houses, all other houses, and angles. Retain major aspects by sampling the local birth day at two-hour intervals plus its final minute: mark aspects present throughout as stable, mark the rest as time-sensitive, and omit applying/separating claims.
- Calculate and persist the versioned natal chart as soon as birth date, birth-time status, birthplace coordinates, and timezone are complete, before intent or model generation. Persist Celestine's five major aspects—conjunction, sextile, square, trine, and opposition—inside the canonical chart JSON alongside positions, houses, nodes, and angles for exact-time charts.
- Retain Celestine for the prototype despite a verified Pluto longitude discrepancy of about 13 arcminutes against Kepler 7.0 and NASA/JPL Horizons for a November 2015 reference chart. Reassess the planetary ephemeris before interpretation becomes sensitive to sign boundaries, house cusps, or tight aspect orbs.
- Use Auth.js with database-backed sessions and Google OAuth as the first authentication method. Email/password authentication remains a separate future slice so registration, verification, recovery, rate limiting, and account linking can be designed together.
- Detailed high-stakes safety architecture remains deferred for the prototype.

## Application architecture

- Use the Next.js App Router with TypeScript and React Server Components by default.
- Use Tailwind CSS for styling and add shadcn/ui components selectively rather than adopting a broad component layer upfront.
- Support English and Spanish from the first onboarding flow. Locale values use stable `en` and `es` identifiers so additional languages can be added later.
- Localized product routes begin with `/{locale}`. The selected locale is stored on the user and in an HTTP-only `astrocoach-locale` cookie so server-rendered document language and navigation remain consistent before full authentication exists.
- The root language-selection route checks the server-side session before rendering. Authenticated users bypass language and sign-in screens and resume through the existing stage-aware landing resolver using their saved locale.
- After onboarding has started, changing the account locale requires an explicit language selection. Cookie-to-account synchronization is limited to the first authenticated handoff, preventing a stale URL or cookie from silently changing an established preference.
- Support system, light, and dark color themes with `next-themes`.
- Store astrology familiarity and communication style on the user profile with defaults of `basic` and `balanced`. Collect them alongside initial intent after birth information and expose the same choices in Account so changes affect future generations without rerunning onboarding.
- Keep the theme control directly available during onboarding, and persist authenticated changes to the user profile. After onboarding, appearance is an Account setting and the shell header uses that space for the user avatar.
- AstroCoach is a mobile-first progressive web application. Every interface starts with phone ergonomics, touch targets, safe-area behavior, and standalone display constraints before adding tablet or desktop enhancements.
- Completed discovery leads through a one-time Chart-at-a-glance reveal and concise product orientation, then into a Home-first application shell rather than directly into chat. The primary mobile navigation remains Home, Conversations, and My Map, with Account available from the header avatar.
- Home is the starting point for a new EXPLORE conversation; Conversations reopens saved threads. My Map is the parent hub for the natal chart and user-owned Patterns, Insights, and Practices. Chart and Map subsection routes keep My Map selected in primary navigation rather than adding another bottom-navigation item.
- Chart-at-a-glance theme cards may start EXPLORE conversations from an editable user-authored prompt. Persist the stable selected theme ID separately as provenance-safe message metadata, pin that theme in first-turn retrieval, and never copy its synthesis into the conversation as if it were user testimony.
- Conversation archiving is recoverable and separate from its cognitive-mode lifecycle status. Archived conversations are read-only, excluded from recent-conversation selection and generation actions, and remain reviewable until restored or permanently deleted. Permanent deletion is available only after archiving and atomically removes the conversation, its messages, and any Map items and Practices rooted in it. Conversation-level actions are grouped in an expandable three-dot row menu so additional actions can be added without crowding the list.
- During prototype testing, each conversation permits at most 15 persisted user messages and 15 persisted AstroCoach messages. Enforce both role limits on the server under serializable transactions and in the mobile composer; stop new turn generation when either side has exhausted its capacity, while allowing a persisted final user message to retry when an assistant slot remains and preserving non-message actions such as candidate evaluation, Map saving, and Practice activation. At the limit, keep the thread reviewable and direct the user to begin a new conversation.
- Export conversations as a versioned JSON document from the conversation row menu, including persisted conversation lifecycle data, the immutable conversation-start context snapshot, and complete message content and metadata. Do not copy current profile preferences onto historical messages; preserve only the settings captured when the conversation began.
- Saved Pattern and Insight wording is user-owned and may be edited directly without another model call or revalidation. Removing a Map item archives it recoverably rather than deleting its wording or provenance, archives Practices rooted in it, and closes active conversations focused on it; archived items can be restored deliberately without silently restarting that work.
- Maintain an installable web app manifest and platform app icons. Add offline caching or push behavior only through deliberate, separately verified slices so stale application code or private user data is not cached accidentally.
- Use Prisma 7 as the ORM and migration system for PostgreSQL. Pin `prisma`, `@prisma/client`, and `@prisma/adapter-pg` to the same exact supported version; do not follow generic `@latest` upgrade suggestions across a Prisma major release without a deliberate application migration, because Prisma 8 uses a different CLI and contract-based workflow. During solo early development, local, preview, and production environments share the Prisma Postgres database connected through the Vercel Marketplace; split environments before broader testing or routine schema-changing previews.
- Use Prisma's PostgreSQL driver adapter. Prefer standard `DATABASE_URL` and `DIRECT_URL` names; accept the Vercel integration's generated `POSTGRES_URL` and resource-prefixed `astro_*` aliases so deployment is not coupled to manually copied secrets.
- Resolve all personal data through the authenticated Auth.js user. The seeded development identity remains fixture data only and must not be used as a runtime identity.
- Account reset preserves the authenticated user, linked OAuth accounts, active sessions, locale, theme, and astrology communication preferences while permanently deleting all birth, onboarding, chart, conversation, Map, and Practice data. It returns the signed-in user to birth-information onboarding and makes a best-effort deletion of linked provider conversation state.

## External services

- Keep all external-service credentials server-only. Never expose them through `NEXT_PUBLIC_*` variables.
- Use a server-mediated external geocoder for prototype birthplace search. Preserve coordinates and an IANA timezone identifier, then resolve the historically applicable offset for the birth date and time.
- Use GeoNames for prototype populated-place search and timezone lookup. Treat its place ID as the submitted selection, re-fetch authoritative coordinates server-side, and derive the historical UTC instant locally from the returned IANA timezone.
- Use the OpenAI Responses API when conversational AI is implemented and request application-facing metadata through Structured Outputs.
- Use one durable OpenAI Conversation per AstroCoach chat. At chat creation, persist an immutable versioned snapshot of the user's complete birth inputs, chart, natal interpretation, onboarding context, starting astrology preferences, and relevant Map context in PostgreSQL; seed that snapshot into the provider conversation once, then send only the current turn and changing application state on later Responses API calls. Keep PostgreSQL as the application source of truth, retain the provider conversation across archive and restore, and best-effort delete its items and conversation after permanent local deletion. Existing chats initialize this state lazily with their stored history. Instructions remain request-specific and must still be supplied on every response. Provider-managed state simplifies request construction but does not eliminate token charges for prior context.
- Retain the complete permitted visible exchange in the provider conversation so the immutable birth/chart snapshot remains available for all 30 possible visible messages. Disable automatic Responses API truncation so an oversized request fails rather than silently dropping the oldest snapshot context. When lazily initializing legacy provider state, retain only the newest 15 user and newest 15 assistant messages in chronological order; legacy threads already at either role limit cannot generate further messages.
- Voice input is transcript-first: authenticated users may record up to two minutes, the temporary audio is sent directly for server-side transcription, and only the resulting editable text enters the existing message flow. Do not persist recordings or send a transcript automatically without user review.
- Use the same voice-recording and transcription behavior in the Home new-conversation composer and existing conversation composer so starting context has input parity.
- The OpenAI model is configured with `OPENAI_MODEL`. The development default is `gpt-5.6-luna`, selected as the current cost-sensitive model; it can be changed without code changes.
- Audio transcription uses the same server-only OpenAI credential and a separately configurable `OPENAI_TRANSCRIBE_MODEL`, defaulting to `gpt-transcribe`.

## Delivery

- The application is designed for Vercel deployment and uses environment-based configuration.
- Development uses npm and commits the generated lockfile.
- The user exclusively handles Git staging, commits, and pushes. The coding agent may inspect Git state but must not mutate it.
- Production builds currently use Next.js's webpack builder and the TypeScript compiler API because the development execution environment blocks Turbopack's internal localhost binding and detached TypeScript CLI process.
- Each implementation slice must leave linting, type checking, and the production build passing.
